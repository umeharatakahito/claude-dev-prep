3〜12分★エージェントとワークフロー（14.7%）

場面答え
手順が決まっているワークフロー（プロンプトの連結）。まずは単純なほうを選ぶ
入力を分類して専門処理へルーティング
独立した作業を同時に／同じ処理を複数回で信頼度を上げる並列化（分割・投票）
サブタスクが入力ごとに変わり、事前に決められないオーケストレーターとワーカー
評価基準が明確で、反復で良くなる（推敲・翻訳）評価者と最適化者のループ（終了条件を必ず持つ）

エージェントループ

  • stop_reason が tool_use → ツール実行 → tool_result を履歴に足して、もう一度呼ぶ。end_turn で終了。
  • 最大回数・予算などの終了条件を、ループ側に持たせる（無限ループ対策）。
  • ★ツール呼び出しが複数（1応答に tool_use が3つ）→ 3つの tool_result を1つの user メッセージにまとめ、tool_use_id で対応させる。
  • ツール失敗は is_error 付きで返し、モデルに立て直させる。

サブエージェント

  • 独立したコンテキストで動き、要点だけを返す → 親のコンテキストが膨らまない。独立した調査は並列にできる。
  • ★親の会話は見えない。目的・対象・制約・期待する出力を、渡す指示の中に全部書く（「ログを調べて」だけでは的外れになる）。

フック

  • 毎回決まって実行される決定論的な制御。「お願い」より確実。
  • ★見せたくない・実行させたくないものはPreToolUse（実行前に止める）。PostToolUse は実行後なので遅い。編集後のリンター実行などは PostToolUse。

その他

  • マネージドエージェントには、セルフホストと Anthropic ホストがある。フレームワークの例: Strands、LangGraph、PydanticAI。

プロンプトキャッシュ（最重要）

  • 効くのは先頭からの完全一致（プレフィックス）。順序は tools → system → messages。
  • ★先頭側（tools・system）が変わると、後ろも全部無効（全部再書き込み）。ツールの説明文の修正も該当。
  • 毎回変わる値（時刻・ID）は後ろ（messages 側）に置く。先頭に置くとヒットしない。
  • 有効期間は標準5分。ヒットで更新される。★アクセス間隔が不規則なら1時間キャッシュ（書き込みは割高なので、再書き込みが減ると得）。
  • 書き込みは通常より割高、読み取りは安い。1回しか使わないなら、かえって損。
  • ★効いたかの確認は usage の cache_read_input_tokens が 0 より大きいか。

モデル・設定の選び方

  • Opus＝難しい推論・エージェント／Sonnet＝バランス／Haiku＝速く安い（大量・単純）。

  • ★単純で速さ優先 → 小さいモデル＋低い effort（思考を使わない）。思考はトークンと待ち時間が増える。
  • 新しいモデルは動作が変わりうる → 評価セットで旧版と比べてから切り替え。バージョンは固定。

21〜28分アプリケーションと統合（33.1%）

API の挙動

  • ステートレス：履歴は毎回 messages に入れて送る。
  • stop_reason：end_turn（完了）／max_tokens（打ち切り）／tool_use（ツール要求）。
  • max_tokens でツール入力が途切れたら、実行しない。上限を上げて再リクエスト。
  • tool_result は user ロールで、tool_use_id を対応させる。
  • ストリーミング：SSE。差分を連結。ツール入力の JSON 断片（input_json_delta）は、ブロック終了まで蓄積してからパース。200 で始まっても、途中でエラーイベントが来うる → 処理を用意。
  • ビジョン：画像は user の content に、画像ブロック（base64 か URL）＋テキストブロック。
  • 同じ大きなファイルを繰り返し使う → Files API（アップロードして file_id で参照）＋キャッシュ。

エラー対応

  • 429／529／5xx（一時的）→ バックオフ付きリトライ＋同時実行数の制限。
  • 413（大きすぎ）→ 入力を縮小。400（不正）・401（認証）→ リトライしても直らない。
  • 並列実行（asyncio.gather）は return_exceptions=True で、1件の失敗で全体が落ちないように。

設計・構成管理

  • ユーザー入力はタグで囲んで指示と分ける。恒久ルールは system に。
  • CLAUDE.md：ユーザー（~/.claude/CLAUDE.md）／プロジェクト／サブディレクトリの階層。長すぎると守られない → 重要な規則に絞り、詳細はスキル等へ。
  • チーム共有の設定 → .claude/settings.json（Git 管理）。個人の上書き → settings.local.json。
  • モデルは日付付きバージョンを固定。プロンプトも Git で管理。
  • プロンプト変更の流れ：評価セットで回帰テスト → 段階的リリース → 監視 → 戻せる状態。
  • 大きなリファクタ：テストを先に整え、小さな単位で変更→テスト→コミット。
  • 会社の統制が要る → Bedrock などクラウド経由。機能の対応状況はプラットフォームごとに違う。
  • 長い会話のコスト → 履歴の末尾付近にキャッシュ区切り＋古いツール結果を刈り込む／要約。無関係な作業は新しいセッションへ。
